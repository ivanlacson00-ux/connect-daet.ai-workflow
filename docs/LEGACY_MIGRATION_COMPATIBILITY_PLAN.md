# Legacy Migration Compatibility Plan

**Branch:** `integration/workflow-restructurev2-main`
**Purpose:** Preserve useful CODEVS behavior while keeping the clean-schema workflow as the source of truth.
**Scope:** Repository evidence only. No Supabase connection or database query was used for this plan. The seven local active migrations are the schema baseline for this analysis; their presence does not independently prove live TEST database state.

## 1. Executive summary

Do not apply any of the 25 archived migrations to the clean schema. They are ordered patches for the old `workflow_submissions` / `profiles.role` system, and many replace one another's functions and policies. Preserve the source files in `supabase/legacy-migrations-archive/from-origin-main/`; implement only reviewed behavior as new, clean-schema migrations with versions after the seven-migration baseline.

The clean schema already models role grants and offices, submissions and immutable versions, attachments metadata, officer-controlled office assignments and routing, review responses and reassessment, overall decisions and audit history, scoped message threads, notifications/delivery history, and a points ledger. Important gaps in the active SQL are Storage bucket/object authorization and checked write operations for messaging and notification delivery. Email, QR retrieval, and demographic fields need clean-schema adaptations; QR and profile demographics are not required by the revised workflow plan. Requirements that the plan leaves open—such as file types, notification recipients, points policy, and private-note visibility—must be decided before implementation.

The app integrated from `origin/main` still calls legacy tables and RPCs. It must be ported to the clean schema rather than making the schema imitate the old application.

## 2. Authoritative references and clean-schema baseline

- [Revised workflow plan](./REVISED_WORKFLOW_PLAN.md) is authoritative for intended behavior. In particular, every submission begins with Tourism Officer review; that officer manually controls office assignments and routing; offices return scoped responses to the Tourism Officer; and only the Tourism Officer makes the overall decision and formal sender change request.
- The seven active migrations are [identity and authority](../supabase/migrations/20261109170834_create_identity_and_authority_model.sql), [submission/version/routing](../supabase/migrations/20261109170923_create_submission_version_and_routing_model.sql), [review and reassessment](../supabase/migrations/20261109171000_create_review_and_reassessment_model.sql), [decisions/history/supporting model](../supabase/migrations/20261109171035_create_decisions_history_and_supporting_model.sql), [RLS/history guards](../supabase/migrations/20261109171148_enable_least_privilege_rls_and_history_guards.sql), [checked workflow operations](../supabase/migrations/20261109171426_add_checked_workflow_operations.sql), and [function EXECUTE restrictions](../supabase/migrations/20261109173844_restrict_workflow_function_execute_privileges.sql).
- The baseline uses `profiles` only for profile identity (`id`, `created_at`); authority comes from `role_grants` and `office_memberships`, not `profiles.role`.
- Core objects include `offices`, `document_types`, `submissions`, `submission_versions`, `attachments`, `submission_version_attachments`, `routing_rounds`, `office_assignments`, office responsibility/authority/revision/event tables, `review_cycles`, `review_responses`, response applicability and reassessment history, `submission_decisions`, `submission_status_history`, `audit_events`, `message_threads`, `thread_participants`, `messages`, `message_attachments`, `notifications`, `notification_deliveries`, `notification_delivery_attempts`, and `points_ledger`.
- Checked operations include `create_submission`, `resubmit_submission`, `create_routing_plan`, `revise_office_responsibility`, `submit_office_response`, `record_officer_response_review`, `start_responsibility_reassessment`, `confirm_response_applicability`, and `record_overall_decision`. These use current identity/role grants and transactionally retain workflow history. The schema does not automatically route based on document type or category.
- Scoped RLS/read helpers cover workflow rows and attachments metadata. The baseline includes an auth-user profile trigger and least-privilege function grants. `record_overall_decision` creates a submitter notification, but there is no general event-to-notification coverage or email-worker operation. The seven-file SQL does **not** define a Storage bucket or `storage.objects` policies, and it does not provide checked message-write operations.
- These are repository findings. The live TEST schema, bucket configuration, Realtime publication, and any out-of-band objects were not inspected here.

## 3. Classification legend

Each archived migration gets one primary classification:

- **A — Already implemented by clean schema:** Its useful workflow capability is already represented by the clean model/operations; do not apply the legacy SQL.
- **B — Useful functionality that needs adaptation:** The behavior can be retained, but its tables, authorization, event model, or UX must be adapted to the clean schema.
- **C — Legacy functionality that conflicts:** It encodes role, approval, routing, or table assumptions contrary to the revised workflow.
- **D — Obsolete or unnecessary:** Not needed for the agreed workflow or superseded by the clean schema. Revisit only if requirements change.

Classification applies to functionality, not to the safety of applying the SQL. **All 25 original migration files remain archived.**

## 6. Required clean-schema equivalents and proposed objects

The clean model already supplies core identity, role grants, office memberships, submissions, versioning, attachment metadata, manual routing, office response/reassessment, final decisions, audit history, message/read models, notification/delivery history, and a points ledger. Avoid duplicate legacy tables such as `workflow_submissions`, `workflow_routing_plans`, `workflow_messages`, `workflow_notifications`, and `workflow_email_outbox`.

Subject to implementation review, the remaining database work is likely to require:

1. **Storage/attachment binding:** private bucket configuration and `storage.objects` read/write policies based on authenticated identity and the clean attachment/submission authorization helpers. Ensure uploaded object keys are safely bound to attachment metadata/version and cannot be swapped or guessed across submissions. No public bucket or client service-role key.
2. **Checked messaging writes:** narrowly scoped SECURITY DEFINER operations for sending messages and, if needed, thread/participant management and read receipts. Enforce `participants` versus `staff_private` visibility in the database; preserve message/attachment history. Keep direct table writes unavailable to broad client roles.
3. **Notification production and delivery:** checked workflow writes that create recipient-scoped `notifications` records in the same transaction when appropriate, plus a service-only worker claim/lease/retry mechanism and provider-event deduplication if email is enabled. Reuse `notification_deliveries` and `notification_delivery_attempts` where they meet the reviewed queue contract; add only missing fields/tables after design.
4. **Optional QR objects:** only after product/security approval, add clean-submission retrieval tokens, revocation/expiry, events, and checked lookup/location/release operations. Hash bearer tokens at rest and avoid exposing attachments directly.
5. **Optional demographics:** no object is required by the current plan; only add profile fields after a separate approved data/privacy specification.
6. **Optional Realtime:** publication configuration for clean tables only if an explicit UX need is established; realtime must not replace RLS or reliable notification delivery.

Any new callable database function needs an explicit signature/authorization review, ownership by the constrained workflow executor where appropriate, `SECURITY DEFINER` with a safe `search_path`, explicit EXECUTE ACLs, PUBLIC/anon restrictions, and regression tests. Use new migration versions after the seven clean migrations; never edit or replay the archived files.

## 7. RLS and Storage requirements

- Keep all workflow tables RLS-protected and scoped by submitter, active role grant, assignment, office membership, and relevant submission version. Do not replace these policies with broad authenticated read/write.
- Keep workflow mutations behind checked operations that derive the caller from database identity, revalidate active grants/memberships, enforce workflow transitions, and record append-only history in the same transaction.
- A submitter may access their own submissions and attachments; the Tourism Officer may coordinate and review; external office members may access only the relevant assigned office's scoped review material. A former/cancelled assignment must not expose unrelated material.
- Only the Tourism Officer may initiate reassessment or issue a formal sender change request. A mandatory denied/unresolved responsibility blocks overall approval; cancellation must not bypass it.
- Create no public storage access. Define a private bucket and object-key convention, enforce ownership and attachment authorization in Storage policies, and preserve access to historical versions only for authorized users.
- Do not allow direct browser writes with a service-role credential. Server-side code using that credential must still perform explicit actor/office/submission authorization because service role bypasses RLS.
- The revised plan leaves file formats, size limits, offline evidence, exact note visibility, notification recipients, and retention details unspecified. Do not hard-code the archived migration's policy values without approval.

## 8. Migration dependencies and recommended implementation order

All archived migrations are dependent patches: the versioned route model precedes dynamic route functions; later migrations replace transition, route, notification, and submission functions; the Storage MIME migration requires an existing `workflow_uploads` bucket; the upload validator depends on that bucket and legacy attachment table; messaging has a separate bucket; email migrations assume an outbox/queue already exists; QR functions assume finalized legacy routes. Applying only selected archived files would still leave unresolved prerequisites and replaced definitions.

Recommended sequence for future work:

1. **Read-only TEST baseline confirmation** before implementation: verify target project, migration history, live Storage buckets/policies, RLS, roles, and publication state. Local SQL is not proof of deployed state.
2. **Resolve open decisions** that affect the feature being built: especially accepted file types/size, private-note participants, notification event recipients/channels, and any QR or demographics scope.
3. **Secure attachment Storage integration** on the clean model; implement and test the user submission/version upload path before dependent attachment features.
4. **Messaging write path and privacy** using the clean thread model, with direct-write denial and storage/attachment checks.
5. **Notification creation and delivery contract**, then server-side email provider/webhook/retry integration using clean notification IDs and idempotent provider events.
6. **Optional realtime**, after choosing clean publication tables and verifying RLS behavior.
7. **Optional QR retrieval** only after approval and after secure attachment access is complete.
8. **Optional demographic data** only after separate privacy and product approval.

Use one reviewed, forward-only migration per cohesive database change, with versions later than the current clean baseline. Do not update migration history manually, reintroduce archived SQL into the active directory, or make production changes as part of TEST work.

|---|---|
| Roles and authentication | Signup creates only the expected profile; role claims are not trusted from user-editable metadata; active/revoked `role_grants` and office membership immediately determine access; unauthorized role/membership changes fail. |
| Submission and attachments | User submission creates the initial version and metadata through the checked operation; duplicate requests are idempotent; another user cannot read, upload to, replace, or delete the file; Tourism Officer and only assigned office members can access allowed records; retained versions remain correctly linked. |
| Storage policies | Bucket is private; unauthenticated, unrelated user, unassigned office, malformed path, mismatched metadata, and unauthorized delete attempts fail; authorized access succeeds; object key cannot be used to bypass `can_read_attachment`; service-role secret is absent from browser bundles. |
| Routing and office response | Submission always enters Tourism Officer initial review; only the Tourism Officer creates/modifies/cancels routes and selects routing mode/offices; simultaneous assignments do not auto-forward; sequential routing waits for officer action; offices cannot decide outside assigned responsibility. |
| Decisions/reassessment | Mandatory denial/unresolved status blocks approval; negative evaluation/recommendation alone does not veto; only Tourism Officer can return/reject/approve overall or initiate reassessment; return creates a new version and selected reassessment cycles while preserving old decisions and audit events. |
| Messaging/private notes | Authorized participants can read/send only in scope; submitters and unrelated offices cannot read staff-private threads; nonparticipants cannot enumerate threads/attachments; message writes and read markers are attributed and auditable. |
| Notifications/email | Only approved event/recipient combinations create notifications; in-app read state is recipient-scoped; retry/worker claims are safe under concurrent jobs; delivery attempts/provider events are idempotent; errors do not disclose secrets or document contents; HTML is escaped and links stay on the application origin. |
| QR, if approved | Expired/revoked/invalid token fails; token storage is hashed; unauthorized lookups do not reveal submission existence or file URLs; access is rate-limited and audited; only approved location/release actors can mutate state. |
| File types, if approved | Approved extensions/content are accepted; mismatched MIME, spoofed extension, oversized, malformed, and disallowed files are rejected consistently; limits are enforced server-side and covered by tests. |
| Demographics, if approved | Only approved fields are collected; validation, least-privilege reads, retention/deletion policy, and privacy behavior are tested; role remains outside profiles. |
| RLS/function privileges | Test as `anon`, `authenticated` user, Tourism Officer, assigned/unassigned external approver, admin, and service worker; confirm unauthorized table writes and function EXECUTE fail, intended operations succeed, and new functions preserve safe owner/search path/ACL expectations. |

## 11. Keep archived permanently

Keep all 25 original files in `supabase/legacy-migrations-archive/from-origin-main/`; none should be moved back or applied. In particular, permanently exclude from the clean migration chain:

- `profiles.role` constraints and `admin_update_profile_role`, profile-role lookup/repair RPCs, and municipal office-specific application roles.
- The five-stage workflow, Mayor approval, admin route-review/approval, old `decide_workflow_submission`, and old route-step decision/completion transitions.
- `workflow_submissions`, `workflow_submission_attachments`, `workflow_routing_plans/steps`, `workflow_messages`, `workflow_notifications`, and `workflow_email_outbox` schemas and their dependent policies/functions.
- Office-to-sender formal requirement requests or automatic office forwarding; neither matches Tourism Officer-controlled change requests and routing.
- The archived Storage policies/bucket assumptions and MIME allowlist as-is. Revisit policy values only after a clean-schema security design and approved file-type decision.
- Demographic fields and QR retrieval SQL unless separately authorized; retaining source history in the archive does not approve those features.

Useful behavior from the archive may be ported, but the port must target the clean schema, follow the revised workflow, and arrive as new reviewed migrations and application changes.
